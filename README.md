# terminal-libghosty

A Windows SSH connection manager with a graphical profile picker and a tabbed terminal workspace for SSH connections and local PowerShell 7 (`pwsh.exe`) sessions. See [desktop UI instructions](docs/desktop-ui.md).

The GUI Connect action and **NEW SSH**/**NEW PWSH** buttons fork the same `terminal-libghosty.exe` with the private `--server` mode, one child per session tab. The parent remains the manager client; each child owns its Direct2D terminal surface, SSH or PowerShell connection, ConPTY session, and Ghostty rendering, embedded in a tab container. A child is tied to the parent process lifetime and is terminated when its tab closes. There is one application executable, not a separately built `terminal-host.exe`. SSH argv comes from `internal/ssh.BuildArgs()` with strict host-key verification. This is an initial embedded renderer: IME, clipboard, mouse reporting/selection, font/DPI handling, and full style fidelity still need work before production acceptance. See [implementation status](docs/implementation-status.md).

The production Go application statically links the official `libghostty-vt` C ABI through cgo, so a release is a single executable and does not require `ghostty-vt.dll` at runtime. `build.ps1` builds `ghostty-vt-static.lib` with Zig 0.17, then builds with `CGO_ENABLED=1` and Zig as the C compiler. When cgo is disabled (`CGO_ENABLED=0`), the host falls back to loading `ghostty-vt.dll` dynamically for development and ABI testing; set `GHOSTTY_VT_DLL` or `TERMINAL_LIBGHOSTY_NATIVE_DIR` in that mode. ConPTY process management and the Ghostty host adapter are implemented in Go. The original `native/` C implementation is retained as the compatibility reference and can still be built/run through CMake for regression comparison; the Go application does not load `terminal_libghosty_session.dll`. See [native build notes](native/README.md).
